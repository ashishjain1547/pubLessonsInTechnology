📝 Integrating GitHub with Blogger Using GitHub Actions

Imagine you write your blog posts as simple files stored in a GitHub repository. Every time you add a new file or tweak an existing one, a robot (a GitHub Action) automatically publishes or updates the corresponding post on your Blogger blog — without you ever needing to log into the Blogger dashboard. This guide explains exactly how to set up that automation, step by step, in plain language.

🎯 What we will cover:
  • How GitHub Actions work (the "robot" that runs when you push changes)
  • How to obtain Blogger API credentials
  • How to structure your repository so each Markdown file maps to one blog post
  • Writing the automation script that handles three situations:
    ✅ New file added → create a new Blogger post
    ✅ Existing file updated → update the matching Blogger post
    🚫 File deleted → do absolutely nothing on Blogger
  • Full, tested code snippets you can copy and adapt

1. Understanding the Big Picture

Before writing a single line of code, let's clarify the three entities that will work together:

  • GitHub Repository: A folder in the cloud where you store your blog posts as files (e.g., Markdown .md files).
  • GitHub Actions: A free automation service from GitHub. You define a workflow (a YAML file) that says: "When someone pushes a change to the repository, run a script."
  • Blogger API: A set of web addresses (endpoints) that allow a program to create, read, update, or delete blog posts on your Blogger blog. Google provides this API for free.

The flow is: You push a file → GitHub Action fires → Script talks to Blogger API → Post appears on your blog.

2. Setting Up Blogger API Credentials

To let your script talk to Blogger, you need a set of digital keys: a Client ID, a Client Secret, and a Refresh Token. These tell Google: "Yes, this program is allowed to post on behalf of my blog."

1 Enable the Blogger API

  1. Visit the Google Cloud Console.
  2. Create a new project (or select an existing one).
  3. Navigate to APIs & Services → Library.
  4. Search for Blogger API v3 and click Enable.

2 Create OAuth 2.0 Credentials

  1. Go to APIs & Services → Credentials.
  2. Click Create Credentials → OAuth client ID.
  3. Configure the consent screen if prompted (choose "External", fill in app name and email — this is just for you, not the public).
  4. For Application type, select Web application.
  5. Add https://developers.google.com/oauthplayground as an authorized redirect URI.
  6. Click Create. Note the Client ID and Client Secret.

3 Obtain a Refresh Token

A refresh token is a long-lived key that lets your script get new access tokens without you being present. We use the OAuth 2.0 Playground to get one:

  1. Go to OAuth 2.0 Playground.
  2. Click the ⚙️ gear icon (settings), check Use your own OAuth credentials, and paste your Client ID and Secret.
  3. In the left panel, find and select Blogger API v3 → https://www.googleapis.com/auth/blogger.
  4. Click Authorize APIs, sign in with the Google account that owns your Blogger blog, and grant permission.
  5. Click Exchange authorization code for tokens.
  6. You will see a Refresh token. Copy it — this is the crucial piece.
⚠️ Keep these secrets safe! You will store the Client ID, Client Secret, and Refresh Token as GitHub Secrets in your repository. Never commit them directly into your code files.

3. Finding Your Blogger Blog ID

Every Blogger blog has a unique numeric Blog ID. To find it:

  1. Go to your Blogger Dashboard.
  2. Click on the blog you want to automate.
  3. Look at the URL in your browser's address bar. It will be something like:
    https://www.blogger.com/blog/posts/12345678901234567890
  4. The long number at the end (12345678901234567890) is your Blog ID.

Store this number as another GitHub Secret named BLOGGER_BLOG_ID.

4. Structuring Your GitHub Repository

We will keep things simple. Each blog post lives as a Markdown file inside a posts/ folder. The filename (without the .md extension) becomes a unique slug that our script uses to track which Blogger post corresponds to which file.

📁 your-blog-repo/ ├── 📁 .github/ │ └── 📁 workflows/ │ └── 📄 blogger-sync.yml ← The GitHub Action workflow ├── 📁 posts/ │ ├── 📄 hello-world.md │ ├── 📄 my-second-post.md │ └── 📄 summer-recipe.md ├── 📄 sync_blogger.py ← The Python script that does the real work └── 📄 requirements.txt ← Python dependencies

Each Markdown file needs a small header section (called front matter) where we specify the post's title and optionally labels. We use YAML format between triple-dashes:

---
title: "Hello, World! My First Automated Post"
labels: ["automation", "github-actions"]
---
This is the **body** of my blog post. I can use _Markdown_ formatting here.

## A Subheading
Content goes here. The script will convert this Markdown to HTML
before sending it to Blogger.
📌 The tracking trick: When the script creates a new post via the Blogger API, Blogger returns a unique post ID. The script then saves that post ID into a small JSON file called post_map.json in the repository root. This file acts as a lookup table: slug → Blogger post ID. On subsequent runs, the script checks this map to know whether it should create a new post or update an existing one.

5. The Heart of the System: sync_blogger.py

This Python script is the brain. It is called by the GitHub Action and receives a list of files that were added, modified, or deleted during the push. It then decides what to do for each file.

Let's build it piece by piece.

5.1 Imports and Configuration

#!/usr/bin/env python3
            """
            sync_blogger.py – Sync Markdown files from a GitHub repo to Blogger.
            Handles: new files (CREATE), modified files (UPDATE), deleted files (IGNORE).
            """

            import os
            import sys
            import json
            import re
            import requests
            import markdown
            import yaml
            from pathlib import Path

            # ── Configuration from environment variables (set by GitHub Secrets) ──
            CLIENT_ID = os.environ["BLOGGER_CLIENT_ID"]
            CLIENT_SECRET = os.environ["BLOGGER_CLIENT_SECRET"]
            REFRESH_TOKEN = os.environ["BLOGGER_REFRESH_TOKEN"]
            BLOG_ID = os.environ["BLOGGER_BLOG_ID"]

            POSTS_DIR = "posts"
            MAP_FILE = "post_map.json"

            BLOGGER_API_BASE = "https://www.googleapis.com/blogger/v3"
            TOKEN_URL = "https://oauth2.googleapis.com/token"

5.2 Getting a Fresh Access Token

The refresh token never expires (unless revoked), but access tokens are short-lived. We exchange our refresh token for a fresh access token on every run: 

def get_access_token():
            """Exchange the refresh token for a new access token."""
            payload = {
            "client_id": CLIENT_ID,
            "client_secret": CLIENT_SECRET,
            "refresh_token": REFRESH_TOKEN,
            "grant_type": "refresh_token",
            }
            response = requests.post(TOKEN_URL, data=payload)
            response.raise_for_status()
            return response.json()["access_token"]

The post map is a simple JSON dictionary: {"hello-world": "9876543210", "summer-recipe": "1234567890"}.

            return json.load(f)

        """Save the slug→post_id mapping back to disk."""

        json.dump(post_map, f, indent=2)

5.4 Parsing a Markdown File (Front Matter + Body)

def parse_markdown_file(filepath):
            """Extract front matter (YAML) and Markdown body from a file."""
            with open(filepath, "r", encoding="utf-8") as f:
            content = f.read()

            # Match front matter between --- delimiters
            match = re.match(r"^---\s*\n(.*?)\n---\s*\n(.*)", content, re.DOTALL)
            if match:
            front_matter_raw = match.group(1)
            body_markdown = match.group(2)
            metadata = yaml.safe_load(front_matter_raw) or {}
            else:
            # If no front matter, use the filename as the title
            metadata = {"title": Path(filepath).stem.replace("-", " ").title()}
            body_markdown = content

            # Convert Markdown body to HTML
            html_body = markdown.markdown(body_markdown, extensions=["extra", "codehilite"])
            return metadata, html_body

5.5 Creating a New Blogger Post (CASE 1: New File)

def create_post(access_token, title, html_body, labels=None):
            """Create a brand new post on Blogger. Returns the new post ID."""
            url = f"{BLOGGER_API_BASE}/blogs/{BLOG_ID}/posts/"
            headers = {
            "Authorization": f"Bearer {access_token}",
            "Content-Type": "application/json",
            }
            post_data = {
            "title": title,
            "content": html_body,
            }
            if labels:
            post_data["labels"] = labels

            response = requests.post(url, headers=headers, json=post_data)
            response.raise_for_status()
            new_post = response.json()
            print(f"✅ Created new post: '{title}' (ID: {new_post['id']})")
            return new_post["id"]

5.6 Updating an Existing Blogger Post (CASE 2: Updated File)

def update_post(access_token, post_id, title, html_body, labels=None):
            """Update an existing post on Blogger."""
            url = f"{BLOGGER_API_BASE}/blogs/{BLOG_ID}/posts/{post_id}"
            headers = {
            "Authorization": f"Bearer {access_token}",
            "Content-Type": "application/json",
            }
            post_data = {
            "title": title,
            "content": html_body,
            }
            if labels:
            post_data["labels"] = labels

            response = requests.put(url, headers=headers, json=post_data)
            response.raise_for_status()
            updated_post = response.json()
            print(f"🔄 Updated post: '{title}' (ID: {updated_post['id']})")

5.7 The Main Orchestrator

This is where the three cases are explicitly handled. The GitHub Action will pass a JSON string containing the lists of added, modified, and deleted files. 

def main():
            # GitHub Actions passes changed files as a JSON string in env vars
            added_files_raw = os.environ.get("ADDED_FILES", "[]")
            modified_files_raw = os.environ.get("MODIFIED_FILES", "[]")
            deleted_files_raw = os.environ.get("DELETED_FILES", "[]")

            added_files = json.loads(added_files_raw)
            modified_files = json.loads(modified_files_raw)
            deleted_files = json.loads(deleted_files_raw)

            # Filter: only consider .md files inside the posts/ directory
            added_posts = [f for f in added_files if f.startswith(POSTS_DIR) and f.endswith(".md")]
            modified_posts = [f for f in modified_files if f.startswith(POSTS_DIR) and f.endswith(".md")]
            deleted_posts = [f for f in deleted_files if f.startswith(POSTS_DIR) and f.endswith(".md")]

            # ── CASE 3: DELETED FILES ──
            # We explicitly DO NOTHING. Just log it for transparency.
            for deleted_file in deleted_posts:
            slug = Path(deleted_file).stem
            print(f"🚫 File deleted: '{deleted_file}' (slug: '{slug}'). No action taken on Blogger.")

            if not added_posts and not modified_posts:
            print("ℹ️ No new or modified post files detected. Exiting.")
            return

            # Get a fresh access token
            access_token = get_access_token()
            post_map = load_post_map()
            map_changed = False

            # ── CASE 1: NEW FILES ──
            for filepath in added_posts:
            slug = Path(filepath).stem
            if slug in post_map:
            # If somehow the slug already exists in the map, treat as an update
            print(f"⚠️ Slug '{slug}' already mapped — updating instead of creating.")
            metadata, html_body = parse_markdown_file(filepath)
            update_post(access_token, post_map[slug], metadata.get("title", slug), html_body, metadata.get("labels"))
            else:
            metadata, html_body = parse_markdown_file(filepath)
            new_id = create_post(access_token, metadata.get("title", slug), html_body, metadata.get("labels"))
            post_map[slug] = new_id
            map_changed = True

            # ── CASE 2: MODIFIED FILES ──
            for filepath in modified_posts:
            slug = Path(filepath).stem
            metadata, html_body = parse_markdown_file(filepath)
            if slug in post_map:
            # Found existing mapping → UPDATE
            update_post(access_token, post_map[slug], metadata.get("title", slug), html_body, metadata.get("labels"))
            else:
            # Modified but no mapping found → treat as new (could happen if map was lost)
            print(f"⚠️ No mapping for slug '{slug}' — creating as new post.")
            new_id = create_post(access_token, metadata.get("title", slug), html_body, metadata.get("labels"))
            post_map[slug] = new_id
            map_changed = True

            # Save the updated post map back to the repository
            if map_changed:
            save_post_map(post_map)
            print("💾 Post map updated and saved.")

            if __name__ == "__main__":
            main()
🧠 Key insight about CASE 3 (deleted files): Notice that deleted_posts is simply logged and then ignored. The script does not delete the corresponding Blogger post. This is a deliberate design choice: deleting a file from your repository should never silently remove content from your live blog. If you ever want to remove a post, you should do it manually via the Blogger dashboard, or add an explicit "draft: true" flag to the front matter and handle that separately.

7. The GitHub Actions Workflow: blogger-sync.yml

This YAML file lives in .github/workflows/ and tells GitHub: "Whenever someone pushes to the main branch, run the sync script." 

name: Sync to Blogger

            on:
            push:
            branches:
            - main
            paths:
            - 'posts/**'           # Only trigger when files in posts/ change
            - 'post_map.json'       # Also trigger if the map itself is updated
            workflow_dispatch:       # Allow manual triggering from the GitHub UI

            jobs:
            sync-blogger:
            runs-on: ubuntu-latest

            steps:
            # Step 1: Check out the repository code
            - name: 📥 Checkout repository
            uses: actions/checkout@v4
            with:
            fetch-depth: 2       # Fetch the last two commits to detect changed files

            # Step 2: Set up Python
            - name: 🐍 Set up Python
            uses: actions/setup-python@v5
            with:
            python-version: '3.11'

            # Step 3: Install dependencies
            - name: 📦 Install Python dependencies
            run: pip install -r requirements.txt

            # Step 4: Detect changed files (added, modified, deleted)
            - name: 🔍 Detect changed files
            id: changed-files
            run: |
            # Compare HEAD~1 (previous commit) with HEAD (current commit)
            ADDED=$(git diff --diff-filter=A --name-only HEAD~1 HEAD | jq -R -s -c 'split("\n")[:-1]')
            MODIFIED=$(git diff --diff-filter=M --name-only HEAD~1 HEAD | jq -R -s -c 'split("\n")[:-1]')
            DELETED=$(git diff --diff-filter=D --name-only HEAD~1 HEAD | jq -R -s -c 'split("\n")[:-1]')
            echo "added=$ADDED" >> $GITHUB_ENV
            echo "modified=$MODIFIED" >> $GITHUB_ENV
            echo "deleted=$DELETED" >> $GITHUB_ENV
            echo "Added files: $ADDED"
            echo "Modified files: $MODIFIED"
            echo "Deleted files: $DELETED"

            # Step 5: Run the sync script
            - name: 🚀 Sync posts to Blogger
            env:
            BLOGGER_CLIENT_ID: ${{ secrets.BLOGGER_CLIENT_ID }}
            BLOGGER_CLIENT_SECRET: ${{ secrets.BLOGGER_CLIENT_SECRET }}
            BLOGGER_REFRESH_TOKEN: ${{ secrets.BLOGGER_REFRESH_TOKEN }}
            BLOGGER_BLOG_ID: ${{ secrets.BLOGGER_BLOG_ID }}
            ADDED_FILES: ${{ env.added }}
            MODIFIED_FILES: ${{ env.modified }}
            DELETED_FILES: ${{ env.deleted }}
            run: python sync_blogger.py

            # Step 6: If post_map.json was updated, commit it back to the repo
            - name: 💾 Commit updated post_map.json
            if: success()
            run: |
            git config user.name "github-actions[bot]"
            git config user.email "github-actions[bot]@users.noreply.github.com"
            git add post_map.json
            if git diff --cached --quiet; then
            echo "No changes to post_map.json"
            else
            git commit -m "📌 Update post_map.json [skip ci]"
            git push
            fi
🔍 How changed files are detected: The git diff --diff-filter=A command lists only added files, --diff-filter=M lists modified files, and --diff-filter=D lists deleted files. We pipe these through jq to convert them into compact JSON arrays that our Python script can easily parse.

Now that everything is wired up, it's time for a test drive.

Test 1: Creating a New Post (CASE 1)

  2. Commit and push to the main branch.
  3. Go to the Actions tab of your repository and watch the workflow run.
  4. Check your Blogger dashboard — a new post should appear!
  5. Verify that post_map.json now contains the slug and the new Blogger post ID.

Test 2: Updating an Existing Post (CASE 2)

  1. Edit my-test-post.md — change some text or the title.
  2. Commit and push.
  3. The workflow should detect the modification and call the update endpoint.
  4. Refresh your blog post — the changes should be reflected.

Test 3: Deleting a File (CASE 3 – No Action)

  1. Delete my-test-post.md from the repository.
  2. Commit and push.
  3. The workflow runs, logs: 🚫 File deleted: 'posts/my-test-post.md' ... No action taken on Blogger.
  4. The original post on Blogger remains untouched — exactly as intended.
⚠️ Important: After Test 3, your post_map.json will still contain the mapping for the deleted file's slug. If you later create a new file with the same slug, the script will update the old Blogger post (because the mapping still exists) rather than creating a new one. This might be exactly what you want (reviving a "hidden" post), or you may want to manually clean up post_map.json if you truly want a fresh start.

10. Going Further: Ideas & Improvements

Once the basic pipeline is working, you can extend it in many ways:

  • Draft Mode: Add a status: draft field to your front matter. If present, the script sends the post as a draft instead of publishing immediately.
  • Image Handling: Upload images to Blogger's media endpoint and embed them into your posts.
  • Scheduled Posts: Include a publish_date in the front matter and use Blogger's published field to schedule posts for the future.
  • Multi-blog Support: Store a blog_id in the front matter to route posts to different Blogger blogs from a single repository.
  • Slug Mapping Without Front Matter: Use the filename as the URL slug on Blogger by setting the title and omitting a custom URL (Blogger auto-generates one from the title).

11. Troubleshooting Common Issues

SymptomLikely CauseFix
Workflow fails with 401 Unauthorized Access token is invalid or refresh token has expired/been revoked Re-generate the refresh token via OAuth Playground; update the BLOGGER_REFRESH_TOKEN secret
404 Not Found when updating Blog ID is wrong or post ID in post_map.json is stale Double-check BLOGGER_BLOG_ID; delete the offending entry from post_map.json to force a fresh create
Workflow doesn't trigger on push The paths filter in the workflow doesn't match your file locations Ensure your post files are inside the posts/ folder (or adjust the paths pattern)
Markdown conversion looks wrong The markdown library doesn't support your syntax Try adding more extensions like pymdownx.superfences or switch to a different converter
Deleted file still triggers an update The workflow is not correctly isolating deleted files Verify the --diff-filter=D logic in the workflow's changed-files detection step

12. Wrapping Up

You now have a fully functional, automated pipeline that turns your GitHub repository into a headless CMS for your Blogger blog. The three core behaviors are crystal clear:

  • 📄 New Markdown file pushed → A fresh Blogger post is created, and its ID is recorded in post_map.json.
  • ✏️ Existing Markdown file modified → The corresponding Blogger post is updated with the new title, content, and labels.
  • 🗑️ Markdown file deleted → Nothing happens on Blogger. The post remains safe, and the deletion is merely logged for your awareness.

This setup gives you the best of both worlds: the power and flexibility of writing in your favorite text editor with version control, combined with the seamless publishing of the Blogger platform. Happy writing — and happy automating! 🚀
